# スポット収集再設計 Phase 1 テスト計画

## 目的

新規 `redesign_v1` ジョブの通常処理を確認し、既存 `legacy_v1` ジョブが従来経路のまま維持されることを確認する。

## 1. DBマイグレーション

- [ ] `spot_import_jobs.pipeline_version` が追加される。
- [ ] マイグレーション前から存在するジョブはすべて `legacy_v1` になる。
- [ ] マイグレーション後に作成したジョブは `redesign_v1` になる。
- [ ] `spot_import_urls.fetched_at / fetched_order` が追加される。
- [ ] `spot_import_page_candidates.extraction_order` が追加される。
- [ ] 既存ページに取得順・抽出順が設定される。
- [ ] `worker_save_merge_progress` 経由で `skipped` を保存できる。
- [ ] 施設単位の失敗がある場合、ジョブ終了時に `final_outcome=partial_error` となる。

## 2. 既存ジョブ互換性

- [ ] 既存の一時停止ジョブは `legacy_v1` のまま。
- [ ] 既存ジョブは旧 `candidate_analysis` 工程を含む従来経路を使う。
- [ ] 既存ジョブの情報統合は旧 `merge-spot-information-v2-worker` を使う。
- [ ] 既存の `relevance_progress` を新形式で上書きしない。

## 3. 新規ジョブの工程

- [ ] URL収集後、施設名抽出へ進む。
- [ ] 施設名抽出完了後、旧 `candidate_analysis` を経由せず情報統合工程へ進む。
- [ ] 施設名は `spot_import_page_candidates` の `extraction_order` 順で処理される。
- [ ] 施設名の重複は文字列完全一致だけで除外される。
- [ ] 表記揺れは別名として残る。

## 4. 関連ページ

- [ ] 収集済みページ全体から関連ページを検索する。
- [ ] タイトル・本文の完全な文字列一致で検索する。
- [ ] 抽出元ページも検索対象に含む。
- [ ] URL正規化後の重複は一件にまとめる。
- [ ] 重複時は収集順で最初の本文だけを代表として使う。
- [ ] ページ順は `fetched_order` 順で維持される。

## 5. ABCD評価

- [ ] 1回のCron実行で最大25ページだけ評価する。
- [ ] Geminiには保存済み本文全体を渡す。
- [ ] 評価完了済みページを通常再開で再評価しない。
- [ ] Gemini失敗1回目・2回目は同じバッチを次回Cronで再試行する。
- [ ] 3回失敗した施設名はエラー状態になり、後続施設へ進む。
- [ ] 評価結果にランク・理由・URL・評価日時が保存される。

## 6. 情報統合

- [ ] ABCD評価完了後の別Cron実行で情報統合する。
- [ ] 1回の実行で1施設名だけ処理する。
- [ ] A→B→Cの順、同ランク内は収集順で選定する。
- [ ] Dとreviewは対象外。
- [ ] 本文文字数だけをUnicodeコードポイント数で計算する。
- [ ] 80,000文字を超える次ページがあれば、そのページ以降をすべて除外する。
- [ ] ページ本文を途中で切らない。
- [ ] 住所は本文から確認できた場合だけ生成される。
- [ ] guide_dataが正式12項目のJSONで保存される。
- [ ] A/B/Cが0件なら `skipped` として保存され、Geminiを呼ばない。
- [ ] Geminiの情報統合失敗1回目・2回目は次回Cronで再試行する。
- [ ] 3回失敗した施設名はエラーになり、後続施設へ進む。

## 7. ジョブ終了

- [ ] 全施設が完了・統合対象外なら `normal_completed`。
- [ ] 施設エラーが残る場合は `partial_error`。
- [ ] 処理対象がないCron実行は何もせず終了する。
- [ ] 全体停止時は実行中の一処理単位を完了してから停止する。

## 8. 本番反映前の確認

- [ ] テストはSupabase開発ブランチで行う。
- [ ] 本番のCron、Edge Functions、DBにはテスト中に変更を加えない。
- [ ] テスト結果を確認してから本番適用の順序を決める。
