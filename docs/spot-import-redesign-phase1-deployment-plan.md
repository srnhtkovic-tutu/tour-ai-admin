## 安全な適用順序（Cron稼働中の段階切替）

このプロジェクトではDispatcherのCronが3分間隔で稼働している。DBマイグレーションだけを先に適用すると、新Dispatcherがまだ存在しない間に作られた新規ジョブを旧Dispatcherが処理する可能性がある。そのため、次の順序にする。

1. `merge-spot-information-v3-worker` をデプロイする。まだDispatcherから呼び出されないため、既存処理への影響はない。
2. 二重経路対応の新Dispatcherをデプロイする。マイグレーション前は `claim_spot_import_execution` が `pipeline_version` を返さないため、新Dispatcherは未設定を `legacy_v1` として扱い、既存処理経路を維持する。
3. Phase 1 DBマイグレーションを適用する。既存ジョブは `legacy_v1`、新規ジョブは `redesign_v1` になる。
4. DBのカラム・関数・既存ジョブのバージョンを確認する。
5. 小規模な新規テストジョブで、`redesign_v1` の経路が選択されることを確認する。
6. 正常系・エラー系・停止再開のテスト計画を実施する。
7. テスト結果をレビューしてから本番適用を別途判断する。

## 既存ジョブの保護

- マイグレーション適用時点で存在するジョブは `legacy_v1` に固定する。
- 一時停止中の既存ジョブを新設計へ自動変換しない。
- 既存ジョブの再開は旧v2 Workerと旧工程を使う。
- 既存ジョブのURL収集・ページ抽出の順序も従来方式を維持する。
- 既存ジョブを新設計へ移す必要がある場合は、対象と再処理範囲を別途確認してから実施する。

## ロールバック時の注意

- Cronを停止またはシステム全体を停止してからコードを戻す。
- `redesign_v1` のジョブが残っている間は、旧Dispatcherだけで処理を再開しない。
- DBマイグレーションはデータ保護のため自動で逆戻ししない。必要な場合は状態とデータを確認して個別対応する。
