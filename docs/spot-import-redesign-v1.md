# 旅つづき スポット収集・抽出・評価・情報統合システム 設計書 第1版

- 作成日: 2026-11-23
- 版数: 1.0
- 対象: 全国の自治体・観光地域向けスポット情報収集・審査システム
- 状態: 基本設計の合意版。実装細部は既存DB・Functionとの照合を継続する。

## 1. 目的と基本原則

地域の公式サイト等からページを収集し、施設名抽出、関連ページ検索、ABCD評価、情報統合を自動化する。地域担当者がAI生成結果を確認・編集・承認し、本番スポット情報へ反映する。

基本原則:
1. 収集済み本文を使い、不要な再取得や別文章の生成を行わない。
2. 施設名は完全一致だけで重複排除し、表記揺れを自動統合しない。
3. 施設名の抽出順とページの収集順を維持する。
4. ABCD評価と情報統合を分離する。
5. DBを処理状態の唯一の管理元とする。
6. 1回のCron実行で一つの処理単位だけを実行する。
7. AI元データと人による編集データを分離する。
8. 再評価に失敗しても以前の正式データと本番情報を保護する。
9. 既存テーブルを優先し、不要な新規テーブルを作らない。
10. 全国で使える汎用設計とし、特定地域名・ドメインをロジックに固定しない。

## 2. 全体工程

1. ページ収集
2. ページ単位の施設名抽出
3. 施設名ごとの関連ページ検索・URL重複排除
4. 25ページ単位のABCD評価
5. 施設名単位の情報統合
6. 人による審査・承認・本番登録

旧candidate_analysis工程は新規ジョブの処理経路から外す。既存ジョブの途中再開互換性のため、既存Function・DB処理を直ちに削除する必要はない。

## 3. 施設名抽出

- 収集済みページをページ単位でGeminiに渡す。
- 本文から旅行者が訪問できる場所・施設名を幅広く抽出する。
- 同一施設名は文字列完全一致のみで重複排除する。
- 例: 「石馬寺」「石馬寺（いしばじ）」「石馬寺・滋賀県東近江市」は別名として扱う。
- 最初に抽出された順番を維持する。
- 住所・公式URL・紹介文の生成はこの工程では行わない。

## 4. 関連ページ検索とURL重複排除

- 施設名ごとに収集済みページ全体を検索し、関連ページ数に固定上限を設けない。
- ページタイトルまたは本文に施設名が含まれるページを検索対象とする。抽出元ページも含める。
- URL正規化は現行方式を基本的に引き継ぐ。具体的ルールは現行コードを確認して維持する。
- 同一URLは一つにまとめ、ABCD評価は一度だけ行う。
- 重複時は収集順で最初のページ本文を代表として使い、後続ページ本文を結合しない。
- ページ順は収集順を維持する。

## 5. ABCD評価

- 施設名ごとの関連ページを25ページ単位でGeminiに渡す。
- 1リクエスト内で各ページを個別に評価する。
- ランクはA / B / C / D / review（内部値は既存のreview_requiredとの互換性を確認）。
- 現行の判定基準・プロンプトを原則引き継ぐ。
- DBに保存されたページ本文をそのまま使用する。評価用の別文章を生成しない。
- 評価結果にランク、評価理由、対象URL、評価日時を保存する。
- 完了済みページは保持し、通常の再開では未評価ページから続ける。
- Geminiエラーは同じ25ページ単位について最大3回まで再試行する。3回失敗したら施設名をエラー状態にして後続施設へ進む。管理者の再開操作で失敗した単位から再開する。

## 6. 情報統合対象ページ

- A→B→Cの順に並べる。
- 同じランク内では元のページ収集順を維持する。
- Dとreviewは統合対象外で、80,000文字にも含めない。
- A/B/Cが1件もない場合はGemini情報統合を行わず、施設名を「統合対象外」として記録する。
- 本文の合計上限は80,000文字。
- 80,000文字は本文だけを数え、ページタイトル・URL等のメタデータは含めない。
- 文字数はUnicodeコードポイント数で数える。
- 次のページを追加すると上限を超える場合、そのページ本文を途中で切らず、その時点で選定を終了する。後続ページも採用しない。

## 7. 情報統合

- 1回のCron実行で1施設名だけを処理する。
- 選定したA/B/Cページ本文を一度のGeminiリクエストで統合する。
- 住所はA/B/C本文から対象スポット自身の住所と確認できる場合だけ取得する。確認できなければ空欄。推測しない。
- officialUrlは対象スポット自身の公式サイトと確認できる場合だけ取得する。判断できなければ空欄。
- guide_dataは次の12項目を維持する:
  1. catchCopy
  2. topReason
  3. highlightPoints
  4. tags
  5. bestSeason
  6. latestTopics
  7. officialUrl
  8. recommendFood
  9. recommendHistory
  10. recommendRelax
  11. recommendActivity
  12. localRecommendation
- 確認できた情報だけを保存し、不明項目は空欄・空配列にする。
- DB保存成功を確認してから施設名を完了とする。Gemini応答だけでは完了扱いにしない。
- 保存先は既存のspot_import_merged_v2。merged_dataはAI元データ、reviewed_dataは人の編集結果。

## 8. 施設単位の状態・エラー

基本状態:
- 未処理
- ABCD評価中
- ABCD評価完了
- 情報統合中
- 完了
- 統合対象外

施設単位でエラーを記録し、後続施設の処理は続ける。正常完了・統合対象外は再処理しない。管理者はエラー施設名を個別または複数選択して再開でき、複数なら元の抽出順に処理する。

ジョブ全体の結果:
- 全施設が完了または統合対象外: normal_completed
- 一通り処理したが施設エラーが残る: partial_error
- 未処理施設が残る: 処理中

情報統合エラーではABCD結果を保持し、情報統合だけを最大3回再試行する。

## 9. Cron・実行制御

- 管理画面からWorker Functionを直接呼び出さない。管理画面はDBに指示を記録する。
- Cron起点のDispatcherがDB状態を確認し、サーバー側で一処理単位を実行する。
- ABCD評価は1施設名の最大25ページ、情報統合は1施設名を1単位とする。
- 1単位完了後にDBへ保存して終了し、次のCronで続ける。
- 全体停止時は実行中の1単位とDB保存を完了してから停止する。
- 処理対象がない場合は何もせず終了し、Cron自体は継続する。
- システム全体で一つの実行ロックを使う。期限切れロックは自動解除せず、異常停止として管理者の確認・手動解除を待つ。

## 10. 再評価・再審査

- 管理者が施設名を個別に選択して再評価を指示する。
- 対象施設名の全関連ページを最初からABCD評価し、新しい評価に基づいて情報統合もやり直す。
- 新しい評価・統合結果は一時保存し、ABCD評価と情報統合が正常完了した後に正式データへ切り替える。
- 再評価中・停止中・エラー中は以前の正式なABCD結果、merged_data、reviewed_data、本番スポット情報を維持する。
- 再評価中の停止は実行中の1単位を完了して一時保存を保持する。
- 正式データ切り替え前なら取り消し可能。取り消し時は一時データだけを破棄し、以前の正式データを維持する。
- Geminiエラーは通常処理と同じ最大3回。管理者が施設名を指定して失敗箇所から再開する。
- 再評価中は同じ施設名の通常情報統合・通常エラー再開を受け付けない。
- 再評価状態は「再評価中」「再評価エラー」「再評価停止中」「再評価完了」として管理者画面に表示する。
- 既存のreviewed_dataは自動上書き・削除しない。既存の人による審査がある施設は再評価完了後に「再審査要」とする。
- 再審査が必要な間は本番スポット情報を維持する。
- 再審査は通常審査と同じ確認・編集・承認操作で完了し、承認された内容を本番へ反映する。
- 複数担当者の同時閲覧・編集は許可し、承認確定時にDBの現在状態を確認して先に確定した結果だけを有効にする。
- 再評価の開始・終了・エラー・再開・取り消しを既存実行履歴に記録する。

## 11. DBと既存システムの扱い

- 既存のspot_import_merged_v2を利用し、新しい審査専用テーブルは作らない。
- DBの具体的なカラム名・型・制約・RLS・保存方法は実際の定義を確認して決める。
- 新しいテーブルは必要性が確認された場合だけ検討する。
- 既存のURL正規化、認証、地域権限、実行ロック、履歴の仕組みを確認して引き継ぐ。
- 本番DB・本番Edge Functions・Cronへの適用は、作業ブランチでのレビューとテスト後に別途実施する。

## 12. 実装順序

1. 現行DB・Edge Functions・Cron・管理画面の調査
2. DBの取得順・抽出順の保存と通常処理の改修
3. 25ページ単位のABCD評価と情報統合の改修
4. 施設単位のエラー・再開・partial_error対応
5. 再評価の一時保存・正式切り替え・停止・再開・取り消し
6. 再審査・本番更新・複数担当者競合制御
7. 管理画面対応
8. 正常系・エラー系・停止再開・再評価・同時操作の総合テスト
