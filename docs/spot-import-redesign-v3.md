# 旅つづき スポット収集・抽出・評価・情報統合システム 設計書 第3版

- 作成日: 2026-11-25
- 版数: 3.0
- 対象: 全国の自治体・観光地域向けスポット情報収集・審査システム
- 状態: 第1版を基礎とし、実装・検証結果を反映した改訂版
- 旧版: `spot-import-redesign-v1.md` は設計経緯の参考資料として保持し、本書と混同しない。

## 1. 第2版の位置付け

本書は第1版の基本設計を引き継ぎつつ、実装後に確認された処理実態と、2026-11-24に合意したエラー・リカバリー方針を反映する。

第1版のうち、特に次の内容は本書で置き換える。

- ABCD評価・情報統合の自動再試行（最大3回）
- ジョブ途中の自動再開・個別バッチ再開
- エラー施設を保存済み進捗から再開する方式
- 再評価機能に関する設計
- 1 Cron実行ごとに25ページのABCD評価を進める方式

再評価機能は今後の実装対象外とする。スポット収集、施設名抽出、関連ページ検索、ABCD評価、情報統合、人による審査というシステムの基本工程に注力する。

## 2. 維持する基本設計

- 全国の自治体・観光地域で使える汎用プログラムとし、地域固有の名称・ドメイン等を処理ロジックに固定しない。
- 既存DBを優先し、不要なテーブルやDBオブジェクトを増やさない。
- DBを処理状態の唯一の管理元とする。
- 管理画面からWorkerを直接呼び出さず、DBに指示を記録し、Cron起点のDispatcherが処理する。
- 1回のCron実行で一つの処理単位を実行する。
- システム全体で一つの実行ロックを使う。
- ロック期限切れや一般エラーは自動解除・自動復旧せず、異常として記録し、管理者の確認を待つ。
- AI元データと人による編集データを分離する。
- 旧ジョブは `legacy_v1`、新規ジョブは `redesign_v1` として処理経路を分ける。

## 3. 工程とAI利用

新規ジョブの工程は次のとおり。

1. `url_collection`: URL収集。Geminiを使用しない。
2. `page_extraction`: 収集済みページ本文から施設名・根拠・カテゴリを抽出。Geminiを使用する。
3. `candidate_analysis`: 施設名候補を文字列完全一致で重複排除し、候補名を確定。Geminiを使用しない。
4. `information_merge`: 施設ごとに関連ページを集め、ABCD評価と情報統合を行う。Geminiを使用する。
5. `human_review`: 人が内容を確認・編集・承認する。

### 3.1 ABCD評価

- 施設名ごとに関連ページを収集順で並べる。
- 同一URLは正規化して重複をまとめる。
- 1回のGemini評価リクエストは最大25ページとする。
- 25ページを超える場合、同一施設のWorker実行内で次のバッチを順番に評価する。
- 完了した評価結果はDBへ保存する。
- Dおよびreview_requiredは情報統合対象外。A/B/Cを情報統合対象とする。
- 関連ページがない、またはA/B/Cがない場合は通常のスキップとし、部分エラーには含めない。

### 3.2 情報統合

- A→B→Cの順に、同じ分類内は元のページ収集順を維持する。
- 本文合計上限は80,000文字。本文を途中で切らず、上限を超える次のページ以降は採用しない。
- A/B/Cの本文を根拠に施設情報とguide_data 12項目を生成する。
- Gemini応答だけでは完了扱いにせず、DB保存成功をもって完了とする。
- 保存先は `spot_import_merged_v2`。AI生成データと人の審査データを分離する。

## 4. 通常処理とエラー方針

通常系を優先し、例外を複雑な自動リカバリーで吸収しない。

- 一般エラーが発生した場合は、その時点でジョブを異常停止する。
- 自動再試行は行わない。
- ジョブ途中からの自動再開、個別バッチ再開は行わない。
- 原因を確認・対処した後、必要に応じてジョブ全体を最初から実行する。
- 施設単位のスキップは、次節に定める情報統合工程の既知タイムアウトに限定する。
- URL収集、ページ抽出、施設名候補分析のタイムアウトは施設単位スキップにせず、一般エラーとして停止する。

## 5. 情報統合の施設単位タイムアウト

### 5.1 スキップ対象

新規ジョブ（`redesign_v1`）の `information_merge` に限り、次の既知タイムアウトを施設単位でスキップする。

1. HTTP 504かつ本文に `Request idle timeout limit` を含む。
2. HTTP 546かつ本文に `wall clock time limit reached` を含む。
3. HTTP 500かつWorker応答JSONの `error` が完全一致で `Signal timed out.`。

3は現行WorkerのGeminiリクエストに設定された `AbortSignal.timeout(90000)` による既知のタイムアウトを対象とする。

次はスキップ対象外とする。

- HTTP 546のうち壁時計時間上限以外のリソース制限
- `Signal timed out.` 以外のHTTP 500
- fetch例外、認証エラー、DBエラー、Geminiのその他エラー
- 情報統合以外の工程で発生したタイムアウト

対象外のエラーは従来どおり異常停止する。

### 5.2 スキップ時の処理

- タイムアウトした施設の `spot_import_merged_v2` レコードを `status='skipped'`、`relevance_status='skipped'` とする。
- `relevance_progress.skip_reason='information_merge_timeout'` を記録する。
- `timeout_type`、エラー詳細、理由、スキップ日時を記録する。
- Dispatcherは当該施設を完了扱いにせず、次の施設へ進む。
- ほかの施設の処理結果には触れない。
- ジョブ終了時、タイムアウトスキップが残っていれば `final_outcome='partial_error'` とする。
- 通常スキップ（`no_related_pages`、`no_abc_pages`等）は部分エラーに含めない。

## 6. ジョブ終了後の施設単位手動再実行

施設単位のリカバリーは、通常処理から切り離した管理者の手動操作とする。

### 6.1 実行条件

- ジョブが `completed`。
- `current_stage='human_review'`。
- `final_outcome='partial_error'`。
- システム実行ロックが `unlocked`。
- 操作ユーザーがシステム管理者。
- 対象施設が未審査（review_status pending）であること。

対象はタイムアウトスキップ、または記録済みの施設単位failed状態とする。通常スキップは対象にしない。

### 6.2 再実行方法

- 対象施設の `spot_import_merged_v2` の情報統合状態だけを初期化する。
- `relevance_results` を空配列にし、`relevance_progress` は旧進捗を消去したうえで `recovery_request` メタデータだけを保持する。旧統合結果・入力元情報・エラー情報を初期化する。
- URL収集、ページ抽出、施設名候補、他施設の統合結果は変更しない。
- 親ジョブは `completed / human_review` のまま維持する。
- 対象施設の `relevance_progress` に再実行要求情報を記録する。
- Dispatcherは同じシステム全体ロックを取得し、再実行要求のある施設だけを通常ジョブとは別経路で選択する。
- 再実行中も親ジョブの状態・工程・審査データを変更しない。
- Workerはその施設の関連ページ検索、ABCD評価、情報統合を最初から実行する。
- 完了済みのほかの施設は再処理しない。ほかのタイムアウトスキップはスキップ状態のまま保持する。
- 再実行の指示者、対象施設、理由、再実行種別を実行履歴に記録する。
- 再実行中の実行権は通常処理と同じシステム全体ロックで管理する。

### 6.3 再実行の結果

- 成功した施設は通常の完了状態にする。
- ほかにエラー施設が残っていれば、ジョブは再び `partial_error` で完了する。
- 対象施設が再び既知タイムアウトになった場合は、再度スキップして後続施設へ進む。
- 再実行中に一般エラーが発生した場合は、従来どおり異常停止する。対象施設が未審査である場合に限りfailedとして記録し、異常ロックを保持する。すでに審査済みのデータは上書きしない。原因確認・対処後、管理者が異常ロックを解除してから施設単位の再実行を改めて指示する。

### 6.4 設けない機能

- 自動再試行
- ジョブ途中の再開
- 個別バッチの再開
- 途中までの評価結果を利用した複雑な部分再開
- 複雑な自動復旧・自動ロールバック

施設単位の手動再実行は、必ず対象施設の情報統合を最初から行う。

## 7. 管理画面

- システム管理者専用の施設単位エラー一覧に、完了済みpartial_errorジョブのタイムアウトスキップ施設を表示する。
- 表示内容は施設名、状態、スキップ理由とする。再実行要求後は「再実行待ち」「再実行中」「再実行完了」または「再実行後もタイムアウト」を表示し、処理中・完了済みの施設に再実行ボタンを表示しない。
- 「この施設を再実行」操作で、施設単位の手動再実行RPCを呼び出す。
- 一般ユーザーには再実行操作を表示しない。
- 異常ロック解除は、古いWorkerが停止していることを確認した後に管理者が行う。通常ジョブは解除後に一時停止状態とし、自動再開しない。施設単位リカバリーの場合は親ジョブがもともと `completed / human_review` のため、その状態を維持する。

## 8. Cron・実行制御

- Cron間隔は3分。
- 実行ロック期限は180秒。
- pg_netのtimeoutは140000ms。
- 既存の正常系設定を維持し、タイムアウト対応のために変更しない。
- 1単位完了後にDBへ保存して終了し、次のCronで次の単位を処理する。
- 施設単位の情報統合Workerは、1施設の関連性評価バッチと情報統合を1回のWorker実行内で完了させる。
- 異常ロックは自動解除しない。管理者が実行履歴・エラー・対象ジョブ・工程を確認し、古いWorkerの停止を確認して手動解除する。

## 9. DB・既存データの扱い

- 既存の `spot_import_merged_v2`、`spot_import_jobs`、実行履歴を利用する。
- 新しい施設単位リトライ専用テーブルは作らない。
- DBオブジェクトの削除・作り直しは行わない。
- 施設単位の手動再実行では対象施設の統合状態だけを初期化する。
- 収集済みURL、抽出結果、候補、他施設の統合結果、人による審査データには触れない。
- 既存の旧ジョブは `legacy_v1` の処理経路を維持する。

- 2026-11-25追補：施設再実行の終了時は親ジョブを `completed / human_review` のまま維持し、未解消エラーの有無から `final_outcome` を再計算する。

- 2026-11-25追補：施設再実行の終了時は、対象施設の状態が `completed` または通常スキップの `skipped` であることを確認してから、親ジョブを `completed / human_review` のまま維持し、未解消エラーの有無から `final_outcome` を再計算する。
